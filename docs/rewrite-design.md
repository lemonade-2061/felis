# felis 作り直し設計書(骨組み)

> 2026-11-09 時点の議論をまとめたもの。実装前に埋めて、固めていく。
>
> 印の意味:
> - **[決定]** ユーザーが決めたこと
> - **[案]** 議論で出た提案。まだ確定していない
> - **[未決]** これから決めること
> - **[ユーザー]** ユーザーが自分の言葉で書くところ

## 0. これは何か

**[決定]** felis をまっさらな状態から作り直す。古いコードは持ち込まず、必要なものは書き直す。

**[決定]** コアは「状態の値」。見た目やアニメーションは、felis が関数やフレームワークを提供して、
その上で組み上げる。undo などは値から出てくる副産物で、中心はこの土台。

**[決定]** デフォルトは軽量。カスタマイズで重くなるのは、使う人が選んだコストとして受け入れる。

**[案]** 一行で言うと「状態を値として持つコンポジタの土台。組み上げたものに undo、プレビュー、保存が付いてくる」。

## 1. 触る体験

**[ユーザー]** felis を触る最初の1分間を言葉で書く。ここから必要な設計を逆算する。

- 起動して最初に何が見えるか:
- 窓を開く、動かす、戻すときの手触り:
- 過去の配置やプレビューにどう入り、どう確定・キャンセルするか:
- カスタマイズするとき、最初に何を書くか:

## 2. 全体構造

**[決定]** 3段に分ける。

```
デフォルト設定   フレームワークで組んだ標準の見た目と動き
      ↑ ユーザーと同じ API を使う
フレームワーク   枠、エフェクト、バネ、遷移の部品
      ↑ 値の差分を受け取る
コア             状態の値、更新、検証、履歴、配置の解決
```

**[案]** 境界の判定基準: 色、角丸、アニメ時間など、見た目の言葉がコアの型に出てきたら違反。

**[案]** コアは Elm の構成に対応させる。

| Elm | felis |
|---|---|
| Model | 状態の値 |
| update | イベント → 新しい値 |
| view | 値 → 画面の宣言(最初は窓と矩形だけ) |

### 2.1 責任とプロセスの線引き

**[決定]** 「どのプロセスで動くか」と「誰の責任か」は別の軸として扱う。
コアは WM より小さく、WM(窓の動作の方針)はコアの上に乗るデフォルト設定の側に置く。

| | felis のプロセス内 | 別プロセス |
|---|---|---|
| **仕組み(固定)** | Wayland、入力、描画、値の適用と検証、履歴 | なし |
| **方針(差し替え可)** | BSP、floating、キー設定、遷移、タイムライン UI | 外部レイアウト(将来) |
| **シェル** | なし | バー、ランチャー、通知、ロック画面 |

**[決定]** 分類を迷ったら次の2つで判断する。一覧で全部を決めようとしない。

1. 差し替えたい人がいそうか → いそうなら方針に置く
2. 窓の中身や全入力など、特権データが要るか → 要るなら felis のプロセス内に置く

コアが持つのは履歴と窓のテクスチャまで。それをどう見せるかは方針の側。

**[案]** シェルは同梱せず、乗るための口を用意する。

| 用途 | 口 |
|---|---|
| バー、壁紙、ランチャーの配置 | `wlr-layer-shell` |
| ロック画面 | `ext-session-lock` |
| 窓の一覧 | `foreign-toplevel` 系 |
| ワークスペース表示 | `ext-workspace` や IPC |
| スクショ、画面共有 | screencopy 系と `xdg-desktop-portal` |
| アイドル検知 | `ext-idle-notify` |

## 3. 状態の4層

**[案]** 次の4つを別物として扱う。undo と保存の対象は「意図」だけ。

| 層 | 中身 | 持ち主 | undo・保存 |
|---|---|---|---|
| 意図(値) | レイアウトの状態、focus | felis | 対象 |
| 解決後の配置 | 窓ごとの矩形 | `resolve` の結果 | 対象外(再計算できる) |
| 表示中 | アニメ途中の位置、速度 | フレームワーク | 対象外 |
| 実測 | アプリが実際に描いたサイズ | アプリ | 対象外 |

## 4. コアの型

**[案]** たたき台。実装しながら変える前提。

```rust
trait Layout {
    type State: Clone + Eq + Serialize + DeserializeOwned;

    fn update(&self, state: &Self::State, event: &LayoutEvent, ctx: &UpdateCtx) -> Self::State;
    fn resolve(&self, state: &Self::State, ctx: &ResolveCtx) -> Vec<Placement>;
}
```

- `State` の中身は各レイアウトに任せる。コアが共通で理解するのは `Placement` だけ
- `LayoutTree` のような二分木をコアの前提にしない(スクロール型やタブ型が乗らないため)
- BSP と floating の両方をこの上に実装して、形を検証する
- 保存した配置への窓の割り当て(`fill`)はレイアウト側の責任

### 4.1 ワークスペースとモニタ

**[決定]** ワークスペースは独立した値で、モニタは今それを映している窓口として扱う。
モニタを抜いてもワークスペースの値は残る。

```rust
struct World {
    workspaces: BTreeMap<WorkspaceId, Workspace>,
    outputs: BTreeMap<OutputName, OutputView>, // 今どのワークスペースを映すか
    focused_output: Option<OutputName>,
}
```

**[決定]** 縦横比が変わるモニタへ移しても、最初は値をそのまま映す。
`ratio` は解像度に依存しないが、縦横比には依存する。`resolve` に画面の情報を渡す形にしておき、
分割の向きの読み替えや、縦横別の配置の記憶は必要になってから足す。

### 4.2 focus

**[決定]** focus を2段に分ける。

| | 中身 | 値に入れるか |
|---|---|---|
| 意図の focus | ワークスペースごとに選ばれている窓1つ | 入れる(undo で戻る) |
| 実効の focus | 実際にキーが届く先 | 入れない(毎回導出する) |

実効の focus は次の優先順位で求める。別の状態としては持たない。

```
ロック画面 > レイヤーの排他入力 > ポップアップ > 意図の focus
```

**[決定]** `Workspace` に `focused: Option<WindowId>` を置き、コアが持つ。
`State` の中身は各レイアウトの自由なので、focus まで任せるとキーの送り先が分からなくなるため。

**[決定]** 方向移動は木ではなく `Placement` の幾何で計算する。どのレイアウトでも同じコードで動き、
タイルと floating の間も移動できる。距離が同じなら最近使った窓を優先する。

**[決定]** 窓を閉じたら、そのワークスペースで最近使った窓へ移る。
最近使った順の一覧は undo と比較の対象から外す。

**[決定]** デフォルトはマウスを乗せると focus(focus follows mouse)。
カーソルを実際に動かしたときだけ移し、アニメで窓がカーソルの下に来ただけでは移さない。
方針の側に置き、設定で変えられるようにする。

### 4.3 イベント

**[決定]** 全部をレイアウトに渡さない。自作レイアウトは undo やモニタのことを考えなくていい。

| 受け取り手 | イベント |
|---|---|
| World だけ | undo、redo、ワークスペース切替、窓のワークスペース間移動、focus 移動、タイルと floating の切替、全画面、最大化、窓を閉じる、モニタの増減 |
| Layout にも渡す | 窓の追加と削除、ヒントの変更、移動、入れ替え、リサイズ、ドラッグ、カスタムコマンド |

```rust
enum LayoutEvent {
    WindowAdded { id: WindowId, hints: WindowHints },
    WindowRemoved { id: WindowId },
    HintsChanged { id: WindowId, hints: WindowHints },  // app_id、最小サイズなど
    Move { id: WindowId, dir: Direction },
    Swap { a: WindowId, b: WindowId },
    Resize { id: WindowId, dir: Direction, delta: f32 },
    DragBegin { id: WindowId, at: Point01 },
    DragUpdate { id: WindowId, at: Point01 },
    DragEnd { id: WindowId, at: Point01 },
    Custom { name: String, args: serde_json::Value },
}
```

**[決定]**

- `update` は純粋関数にする。時計、乱数、ファイルを中で読まない。時刻が要るならイベントに持たせる
- `DragUpdate` は1フレーム1回にまとめる。`DragBegin` から `DragEnd` までで履歴は1ステップ
- キー設定は「キーとコマンドの対応表」というデータにする。未知の `Custom` はログを出して無視する
- 座標は `Point01` で渡し、レイアウトがピクセルや出力を知らなくて済むようにする
- `WindowHints` にタイトルは最初は入れない。必要になったら足す
- 基本操作として移動、入れ替え、リサイズ、floating 切替、全画面、最大化を最初から入れる
- タブ、グループ、スクラッチパッドは最初は入れない

### 4.4 State の表現

**[案]** BSP の状態は再帰木1本で持つ。arena、親ポインタ、`free_list`、zipper は使わない。
focus が `World` に移り、方向移動も `Placement` で計算するので、木を上に登る処理がないため。

```rust
enum Tree<L> {
    Leaf(L),
    Split { axis: Axis, ratio: Ratio, first: Box<Tree<L>>, second: Box<Tree<L>> },
}

struct BspState { root: Option<Tree<WindowId>> }  // 実行時も undo もこれ
type SavedBsp = Option<Tree<Binding>>;            // 保存用は葉を写すだけ

struct Workspace {
    tiling: TilingState,      // 最初は BspState に固定
    floating: FloatingState,  // Vec<(WindowId, Rect01)>。順番が重なり順
    focused: Option<WindowId>,
}
```

- `Ratio` は 0.05〜0.95 の範囲でしか作れない専用の型にする。読み込みの検証もここで済ませる
- floating も `Layout` の1つとして実装する
- レイアウトを差し替える層は、2個目のタイルレイアウトを作るときに足す

**[決定]** 新しい窓は focus 中の窓を分割して置く。

**[案]** 分割の向きは窓を追加する時点で、枠が横長なら左右、縦長なら上下で決めて値に固定する。
`resolve` のたびに決め直すと、リサイズで縦横比が入れ替わった瞬間に配置が飛ぶため。
`update` は純粋関数のまま、focus と画面の縦横比を `UpdateCtx` で受け取る。

```rust
struct UpdateCtx {
    focused: Option<WindowId>,
    aspect: f32,  // 幅 / 高さ。ピクセルは渡さない
}
```

## 5. コアからフレームワークへの契約

**[案]** 渡すものは3つ。

| 渡すもの | 中身 |
|---|---|
| 前後の配置 | 窓ごとの矩形 |
| 差分 | 移動、リサイズ、開いた、閉じた |
| 変更の理由 | 通常操作、undo、新しい窓など |

返すのは宣言だけ。毎フレームの計算は Rust が行う。

```rust
fn transition(change: &Change, cause: Cause) -> Animation {
    match (change, cause) {
        (Change::Moved { .. }, Cause::Undo) => spring(STIFF),
        (Change::Opened { .. }, _) => fade_in().and(scale_from(0.95)),
        _ => spring(DEFAULT),
    }
}
```

コア側で用意する必要があるもの:

- 閉じた窓の最後のテクスチャの保持
- アニメ途中で目標を差し替える仕組み
- アニメ中は古い絵を拡大縮小し、`configure` は最後に1回だけ送る仕組み

**[未決]** 見た目の宣言(枠、エフェクト)の形。`view` をどこまで広げるか。

## 6. 履歴

**[案]** 前の設計から引き継ぐ候補(`docs/design.md`、`docs/layout-as-value.md`)。

- スナップショット方式。逆コマンドは採らない
- focus の移動は積まず、スナップショットに focus を含める
- before == after なら積まない
- ドラッグは押してから離すまでで1ステップ
- キーリピートの連続操作はまとめる

**[案]** 記録のタイミングは、入力経路にフックせず「状態が落ち着いた時点」にする。IPC を足しても同じ扱いにできる。
新しい窓など、システム起因の変更を履歴から外す方法は別に決める。

**[案]** 木の操作と、表示だけの操作(スクロール位置など)は履歴を分ける。

**[決定]** undo の範囲はワークスペース単位。今見ているワークスペースの操作だけを戻す。

**[案]** 履歴の保存自体は全体で1本にし、各記録に「触ったワークスペース」を持たせる。
ワークスペース間で窓を動かす操作は、両側をまとめて戻す。

**[案]** 戻した値と今の窓が食い違うときは、新しいアルゴリズムを作らず既存のイベントで埋める。
自作レイアウトは何も書かなくても正しく動く。

1. 保存した値をそのまま戻す
2. もう存在しない窓について `WindowRemoved` を流す
3. 値に入っていない新しい窓について `WindowAdded` を流す

**[案]**

| 項目 | 内容 |
|---|---|
| 積む対象 | ユーザーの操作で、前後の値が変わったものだけ |
| 積まないもの | 窓の開閉、focus だけの移動、モニタの増減 |
| redo | 新しい操作をしたら消える |
| 上限 | 全体で 200 手。古いものから捨てる |
| 再起動後 | 残さない。`WindowId` が別物になるため |
| ドラッグ中やロック中の undo | 無視する |
| 全画面、最大化 | `Workspace` の値に入れて undo の対象にする |

## 7. アプリの都合

### 7.1 サイズの提案と応答

Wayland ではコンポジタはサイズを提案するだけで、実際の大きさはアプリが決める。

**[決定]** 次の方向で作り始める。実機で挙動を見て調整する前提。

| 場面 | 方針 |
|---|---|
| 枠より小さい | 枠の中央に置く |
| 枠より大きい | 枠で切り取る |
| 応答がない | 150ms で打ち切る(値は触って調整) |

一括反映の流れ:

1. 新しい配置を計算して、全部の窓に `configure` を送る
2. 応答が揃うまで古い配置のまま表示する
3. 揃うか打ち切り時間が来たら、一括で切り替える
4. 間に合わなかった窓は古い絵のまま新しい枠に入れ、上のルールで表示する

タイル中の窓には `xdg_toplevel` の `tiled_*` を送る。`xdg-decoration` ではサーバー側描画を要求し、
デフォルトの見た目は枠線だけにする。

### 7.1.1 スケール

**[決定]** 値の層はスケールに依存しない。考えるのは配置を解決したあとだけ。

- レイアウトは論理座標の小数で計算し、コアが物理ピクセルに丸める
- 丸めるのはサイズではなく辺の位置。隣り合う窓に隙間を作らない
- 窓の配置は必ず物理ピクセルの整数に揃える(中央寄せでも同じ)
- 判定は物理ピクセルで行う。2物理px以内のズレは「ぴったり」扱いにする
- 枠線の太さは論理ピクセルで指定し、最低1物理pxにする
- `UpdateCtx` の `aspect` は回転後の値にする
- 分数スケールは `wp_fractional_scale` で伝える。非対応のアプリは拡大してにじむのを受け入れる

### 7.2 窓の分類

**[案]** 木に入れる前に窓を分類する。

| 分類 | 例 | 扱い |
|---|---|---|
| タイル | ブラウザ、ターミナル本体 | レイアウトに入れる。保存も対象 |
| floating | ダイアログ、親窓がある窓、固定サイズの窓 | タイルに入れない |
| 管理しない | X11 の自分で位置を決めるポップアップ | 値に入れない |

- `app_id` は作成時に届かないことがあるので、最初の commit を待って分類するか、後から変えられる形にする
- レイアウトは `WindowId` だけを知る。Wayland 窓か X11 窓かの違いは `WindowRegistry` に閉じ込める

**[未決]** XWayland をいつ入れるか。

## 8. 描画と軽さ

**[決定]** デフォルトは軽量。

**[案]** 原則は「使った分だけ払う」。オフの機能は描画経路に存在しない。

| 項目 | 初期状態 |
|---|---|
| 枠 | 単色 |
| アニメーション | オン(短め)、完全オフ可 |
| 角丸、影、blur、カスタムシェーダ | オフ |

**[案]** 実装方針

- 描画は smithay の `DrmCompositor` と `OutputDamageTracker` に任せる
- 変化があるときだけ次のフレームを予約する
- 効果は窓やルール単位。全画面の窓にはかけず、direct scanout を守る
- 常時かかる効果は offscreen を避ける。短いアニメやプレビューは許す
- blur を入れるなら最初は xray 方式
- overlay plane は後回し
- damage と scanout の可視化を最初に作る

**[案]** イベントループを止めない

- 毎フレームの処理は最小限、操作ごとの処理は軽いものだけ、ディスクや学習はスレッドへ
- ポインタ入力は1フレーム1回にまとめる

**[案]** 基準

- 変化がない画面では描画回数 0
- 全画面アプリでは、対応環境で direct scanout を維持
- デフォルト設定のアニメ中はフレームを落とさない
- 具体的なメモリや GPU の目標値は、実機で測れるようになってから決める

## 9. 拡張の境界

**[案]**

- 最初は Rust の trait で作り、後から同じ値の約束をソケットやスクリプトに載せる
- 外に見せるのは値の形式とバージョンだけ。内部は自由に変えられるようにする
- 拡張が返した値は検証する。外部プロセスにはタイムアウトを付け、固まったら前の値で動き続ける
- 毎フレーム動くユーザーコードは許さない
- レイアウトの持ち主は1つ。他の拡張は変換を順番にかける
- 設定の読み込みに失敗したら、前の状態で動き続ける
- `.so` プラグインは採らない

**[未決]** 拡張を書く人の想定と、スクリプトの入口を作る時期。

## 10. セキュリティ

**[決定]** 作りながら考える。下は忘れないためのメモ。

**[案]** 守るもの: 入力、画面、セッション。信用しないもの: クライアント、読み込むファイル、拡張。

- 保存ファイルに起動コマンドを入れない
- `app_id` は自己申告なので、権限の判断に使わない
- 読み込んだ値は実行時の型にする前に検証する(`ratio` の範囲など)
- ロック中は undo と復元を動かさない。focus の変更は1箇所を通す
- クライアントの入力で panic しない
- 特権プロトコルは、許可するクライアントを決めてから実装する
- IPC ソケットは `$XDG_RUNTIME_DIR` に置き、読み取りと操作を分ける
- キー入力やウィンドウタイトルをログに出さない
- root では動かさず、libseat を使う

## 11. アルゴリズム候補

**[案]** 設計を縛らないよう、`resolve` の差し替えで後から足す。

| アイデア | 使うもの |
|---|---|
| 賢い focus 移動 | 幾何スコア + 最近使った順 |
| 最小移動の復元 | ハンガリアン法 |
| 割り込めるアニメーション | バネ物理 |
| 最小サイズに強いタイル | 制約ソルバ |
| 宣言的な整形ルール | 木の書き換え(適用回数に上限) |
| 使う窓ほど大きく | treemap |
| 重ならない自動配置 | 最大空き矩形、力学モデル |
| 次の配置の予測 | 共起の統計(`app_id` のみ、ローカルのみ) |
| 入力遅延の自動調整 | 描画時間の統計的予測 |

**[案]** 自動整列や予測は勝手に適用しない。提案、プレビュー、undo の組み合わせで見せる。

## 12. 進め方

**[案]** 設計の範囲: 「実機で起動して、undo と保存・復元が動くまで」。それ以降は作りながら決める。

1. DRM、セッション、VT 切り替えを使い捨ての小さな実験で触る
2. 状態の値、`update`、`resolve` を Wayland 抜きで作り、テストする
3. BSP と floating をその上に実装する
4. 実機バックエンドに接続する
5. 履歴と保存・復元
6. 前後の差分と、バネの遷移
7. 単色の枠

最初のゴール: 遷移を10行で自作できる。

**[決定]** 古いコードは持ち込まない。レイアウトのテストも新しい設計に合わせて書き直す。
